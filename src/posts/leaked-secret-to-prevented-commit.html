How one commit exposed a problem (and how to stop it)

A single commit can expose production credentials that stay valid for months or years. Not hypothetical—it happens constantly in open-source repos, and when it does, maintainers face the scramble: revoke, rotate, audit, and hope nothing was compromised.

I recently went through this with a real open-source project. Not my project, but I found the leaked credentials during a scan and responsibly reported them. What followed was a textbook example of how teams should handle credential exposure—and it taught me a lot about what works in security response.

What happened

A secret scanner found GitHub OAuth credentials buried in historical commits of a public repository. Not just one commit—multiple commits spanning years, going back to 2020. Each credential was marked as verified and active by the scanning engine, meaning it had been tested against the live GitHub API and confirmed to work.

The credentials had been sitting there, accessible to anyone who cloned the repo. The exposure window was years.

I filed the report confidentially with the maintainers and waited. They responded fast. Within hours, they confirmed the credentials were no longer valid—they'd already been expired and revoked. They also said they were adding automated secret scanning to their pipeline to prevent this from happening again.

That's the right response. Speed + transparency + prevention.

How detection actually works

Secret scanning isn't just pattern matching anymore. Modern tools do two things in parallel:

TruffleHog-style detection looks for recognizable patterns (OAuth IDs, Azure secrets, API keys) and then actually validates them. When it finds something that looks like a GitHub OAuth token, it tries to authenticate with it. If it works, it marks the finding as "Verified." This cuts through noise—you're not wasting time on false positives.

Gitleaks-style detection casts a wider net. It's pattern-and-entropy based, catches a broader set of secret types, and is fast. Often catches things the narrow detectors miss.

The real power comes when you combine both tools and deduplicate the results. Something like Seraphix pulls findings from TruffleHog and Gitleaks, deduplicates them, and enriches each finding with metadata: timestamp, commit hash, file path, line number, and verification status. Now triage becomes simple. You see immediately: Is this verified? How old is it? Where is it?

In this case, both scanners flagged the same credentials with verified status. High confidence. Urgent.

Triage: What actually matters

When a scanner flags something, you need to decide fast: Is this real, and how bad is it?

Look for these signals in the findings:

  • Detector type: OAuth? Azure? AWS? Different credentials need different rotations.
  • Verification status: Can the scanner actually confirm it works? "Verified: true" means it's live. Act immediately.
  • Timestamp: When was it first exposed? Days? Years? Longer exposure = bigger problem.
  • Location: Is it in config files, source code, dependencies? Public repo or private?

In this case: verified OAuth credentials in a public repo, exposed for years across multiple commits. The decision was obvious. Rotate now.

How to disclose (and how not to)

File the report confidentially. No public GitHub issue, no Twitter. The maintainers need time to rotate before the world knows a secret was exposed. Public disclosure before remediation just puts their users at risk.

I reported it confidentially, and the maintainers got back to me within hours. They confirmed the credentials were no longer usable—already revoked. They also committed to adding secret scanning in CI/CD to catch this before it ever reaches a commit.

That's the whole cycle: report privately, rotate fast, then build prevention so it doesn't happen again. It's collaborative instead of adversarial, and it actually works.

Rotation isn't enough

Revoking a credential stops future abuse, but it's only the first step. After that, you need:

  • Audit the logs. Check if anyone actually used the exposed credential. Unusual IP addresses? Unexpected API calls? Weird timestamps?
  • Rewrite history. Use git filter-repo to purge the secret from every commit, every branch. Then force-push and ask everyone to re-clone. It's a hassle, but it removes the secret from public view permanently.
  • Prevent next time. This is the real fix. Add pre-commit hooks and CI-level secret scanning so the secret never reaches a commit in the first place.

The first two are damage control. The third is the actual solution.

Prevention Strategy: Pre-Commit Secret Scanning

The practical fix: Pre-commit secret scanning

The best place to stop a secret is before it ever hits git. A pre-commit hook runs on your local machine when you try to commit—if it finds something that looks like a secret, it blocks the commit.

Why this matters: immediate feedback in your own editor, no waiting for CI. And you can customize rules for your own infrastructure. Plus, if CI catches a secret, it's already in the history. Pre-commit wins.

Install and Test

If you're using Gitleaks, the gitleaks-pre-commit-hook repository provides a curl-based install helper:

curl -sSL https://raw.githubusercontent.com/AmedeoV/gitleaks-pre-commit-hook/main/install.sh | bash

Done. Now Gitleaks runs on every commit.

What happens

Try to commit something with a secret in it:

$ git commit -m "Add config"
[FAIL] Gitleaks scan detected a potential secret:
  File: config.json
  Pattern: AWS_ACCESS_KEY_ID
  Line: 42
Commit blocked.

Commit doesn't go through. You remove the secret, add it to .gitignore, or add it to your allowlist if it's a fake token for tests. Then you can commit.

The bypass

git commit --no-verify skips the hook. Don't do this with real secrets. If you need to do it, your team should have a code review policy that flags --no-verify commits in PRs. Document exceptions (test fixtures, etc.) and add them to an allowlist so Gitleaks knows they're safe.[HOW-TO] Pre-commit hooks are strong, but not foolproof. Pair them with CI-level scanning:

  1. Pre-commit: Gitleaks hook stops developers before they commit.

    2. Layer it: pre-commit + CI + monitoring

    Pre-commit catches most secrets before they're committed. But add layers:

    • Pre-commit on local machines: Gitleaks hook blocks suspicious commits immediately.
    • CI on every push: Run Gitleaks or TruffleHog again with stricter rules. Catch anything that slipped through.
    • Post-deploy monitoring: Use GitGuardian or GitHub's secret scanning to alert you if your actual secrets ever hit the internet.

    For teams:

      Why this matters: the risks

      Exposed OAuth credentials can be used to impersonate your app in authorization flows and harvest user tokens. Attackers can access your data at higher API rate limits. They can build profiles of your infrastructure and team.

      For cloud credentials like Azure or AWS, the risk is different: direct access to your infrastructure, databases, and services. The exposure window here was years.

      The good news: in this case, the maintainers rotated fast and added prevention. No confirmed unauthorized use. But the risk was real, and catching it early mattered.

      Lessons Learned and Action Items

      [CONFIRMED] The maintainers demonstrated a strong response:

      • Immediate credential revocation.
      • Pipeline hardening (adding secret scanning).
      • Transparent communication with the reporter.

      This case shows what good looks like. For your team, the action checklist is:

      1. Scan your history now: Run TruffleHog or Gitleaks against all your repositories, including private ones. Look for verified findings.
      2. Rotate any findings: Do not delay. Treat verified credentials as compromised.
      3. Add pre-commit scanning: Install a pre-commit hook in all team repositories this week.
      4. Enforce CI scanning: Make secret scanning a required check in your CI/CD pipeline.
      5. Document your process: Create a runbook: "If a secret is found, here's who we notify, how we rotate, and what we audit."

      The real payoff: prevention

      A secret takes minutes to create and months to discover. When you finally find it, you're in crisis mode: rotate now, audit for abuse, rewrite history, hope nothing was exploited.

      Pre-commit hooks change the equation. Secrets get caught before they ever hit git. No history to rewrite, no exposure window to audit. Just "secret blocked, remove it or add it to the allowlist."

      This case showed what good incident response looks like—fast, transparent, collaborative. But the real lesson is that you can prevent 99% of this with basic tooling.
