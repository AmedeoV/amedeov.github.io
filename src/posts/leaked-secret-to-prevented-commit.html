When a secret leaks and the team handles it right

I've already scanned a lot of GitHub repositories and found plenty of exposed secrets. So naturally, I wanted to try the same approach on GitLab. I built a custom scanner based on TruffleHog that crawls public repos, detects credentials, and verifies them against live services. If TruffleHog says "Verified: true," that secret is active right now.

One of the first things it flagged: Azure Service Principal credentials in Appsemble's public GitLab repository. Client secret, client ID, tenant ID—the full set. Verified as active. Sitting in git history across multiple commits.

How Appsemble handled it

I reported the findings confidentially. The response was fast and exactly what you'd want to see from any team:

"Thank you very much for letting us know about the exposed credentials. The Azure ones were most critical and have been expired so they can no longer be used."

They immediately expired the Azure credentials, confirmed the OAuth tokens were already rotated, and committed to adding automated secret scanning to their pipeline. That's textbook incident response—acknowledge, revoke, prevent. No delays, no defensiveness, just action.

The real-world impact

To understand why the maintainer called the Azure credentials "most critical"—these were tied to mail services. An Azure Service Principal with mail permissions can send emails as the organization. In this case, the credentials belonged to a deployment involving a public sector client. Someone with access to those credentials could have impersonated official communications from a government entity.

The client's investigation into whether the credentials were misused during the exposure window is still ongoing. Out of respect for that process—and at the maintainer's request—I'm not naming the specific client or repository. What matters is that the credentials have been expired and can no longer be used.

This is how you want a team to respond. Seriously. Most projects I've reported to aren't nearly this fast or transparent.

Why this matters more now: AI agents write code too

Here's the thing that's changed in the last year: we all use AI agents now. Copilot, Claude, Cursor, Windsurf—they generate code, they commit, they push. And they don't know your secrets from your source code.

An agent might pull a credential from a config file and drop it into a test. It might hardcode an API key because you asked it to "make this work." It might copy a connection string into a README example. And if you're running an agentic workflow that commits automatically? That secret is in your history before you even notice.

This is why pre-commit hooks aren't optional anymore. They're your last line of defense before something hits git—whether it was typed by a human or generated by an AI.

The fix: one command

I maintain a gitleaks-pre-commit-hook that installs in one line:

curl -sSL https://raw.githubusercontent.com/AmedeoV/gitleaks-pre-commit-hook/main/install.sh | bash

Now every commit gets scanned before it touches git. If Gitleaks finds something that looks like a secret, the commit is blocked:

$ git commit -m "Add config"
[FAIL] Gitleaks detected a potential secret:
  File: config.json
  Pattern: AWS_ACCESS_KEY_ID
  Line: 42
Commit blocked.

You fix it, then commit again. Simple. Whether you wrote that line or your AI agent did—it gets caught either way.

Don't rely on one layer

Pre-commit hooks are great but not bulletproof (--no-verify exists). Layer your defenses:

  • Pre-commit: Catches secrets before they enter git history.
  • CI pipeline: Runs TruffleHog or Gitleaks on every push. Catches what slipped through.
  • Platform scanning: GitHub/GitLab secret scanning as a safety net.

The Appsemble case is a great example of what happens when you catch something early and respond well. But the better story is never having to respond at all.
